## 4. 贯穿全表的设计决策

| 决策 | 内容 | 理由 |
| --- | --- | --- |
| **主键用 UUID** | `String @id @default(uuid()) @db.Uuid` | 避免 JS `BigInt` 无法 `JSON.stringify` 的经典坑；API 不暴露自增序号；主键不连续、不可枚举 |
| **时间统一 timestamptz** | 所有时间列 `@db.Timestamptz(3)` | 存 UTC，显示时按 `Asia/Shanghai` 转换，跨时区/跨环境不会错 |
| **软删除** | 业务表统一 `deleted_at`，NULL = 未删除 | 回收站、恢复、审计的基础 |
| **名称唯一用部分唯一索引** | 分类名、标签名只约束 `deleted_at IS NULL` 的行 | 普通 UNIQUE 做不到：NULL 在唯一索引中互不相等，软删除后会与新建同名冲突 |
| **乐观锁** | `work_items.version` | FR-2.14 并发编辑保护 |
| **`source` 字段** | 状态日志、审计日志、评论都带 `ChangeSource` | 时间线上能显示"这条状态是 AI 助手改的"，出了问题可追溯到底是谁改的 |
| **一对默认状态** | 部分唯一索引保证 `is_default = true` 最多一行 | 新建工作项的默认状态必须唯一确定 |
| **模糊检索** | 4 个 `gin_trgm_ops` GIN 索引（标题/描述/编号/评论） | FR-5.5 搜索 + AI 助手 `search_work_items` 工具的底层依赖（`§16.3`） |

## 5. 与需求文档草案的偏差（2 处，均为刻意）

### 5.1 附件改为两个可空外键（原草案：多态 `owner_type` + `owner_id`）

```
原草案：  attachments(owner_type 'work_item'|'comment', owner_id)
落地版：  attachments(work_item_id?, comment_id?)
```

理由：

1. **有真外键**，杜绝孤儿行（多态写法数据库层面无法约束）；
2. `onDelete: Cascade` 让"工作项彻底删除 → 附件记录自动清理"（FR-4.13）天然成立，不必写定时任务扫孤儿文件；
3. Prisma 能表达关系，`workItem.attachments` 可直接查询，应用层不用手写多态条件。

约束用 CHECK 表达：**至多一个宿主非空**（两个都为空 = 已上传但尚未绑定的暂存文件，契合两阶段上传流程）。

### 5.2 优先级用固定枚举，不放进可配置字典

需求文档 FR-11.1 把"优先级"列进了字典管理，但 §3.1 字段表又写明优先级是枚举（紧急/高/中/低，颜色区分）。落地时按 §3.1 处理：**优先级是固定四级枚举**。

理由：优先级的语义参与排序与统计（`@@index([priority, dueAt])`），做成可配置字典会让排序失去确定含义。可配置的是**类型**与**来源**（存 `String`，值来自 `dictionaries` 表）。

如果你确实需要可配置优先级，改动很小（换成 `priorityId` 外键 + 字典表），说一声即可。

## 6. 数据库级约束与索引

Prisma schema 语法表达不了的部分，放在初始迁移里（源文件保留在 `prisma/sql/`，便于复现与审阅）：

| 对象 | 内容 | 为什么需要 |
| --- | --- | --- |
| `pg_trgm` 扩展 | `CREATE EXTENSION IF NOT EXISTS pg_trgm` | 必须先于 trigram 索引创建；是 trusted extension，库 owner 即可建，不需要超级用户 |
| `categories_name_active_uidx` | 部分唯一索引（`WHERE deleted_at IS NULL`） | 软删除后可重建同名分类 |
| `tags_name_active_uidx` | 同上 | 同上 |
| `work_item_statuses_one_default_uidx` | 部分唯一索引（`WHERE is_default = true`） | 默认状态只能有一个 |
| `work_items_progress_check` | `progress BETWEEN 0 AND 100` | 进度越界在库层拦截 |
| `work_items_hours_check` | 预估/实际工时非负 | 同上 |
| `attachments_single_owner_check` | 至多一个宿主 | 见 §5.1 |

> **已验证不会产生 drift**：加完自定义 SQL 后跑 `prisma migrate dev --create-only` 探针，生成的是空迁移 —— Prisma 不会试图删除它不认识的对象。所以今后正常 `migrate dev` 是安全的。

## 7. 常用命令

```powershell
cd apps\api

npm run prisma:validate     # 校验 schema 语法
npm run prisma:format       # 格式化（会重排对齐，改完记得先 format）
npm run migrate:dev         # 开发期：改完 schema 生成并应用迁移
npm run migrate:deploy      # 部署期：只应用已有迁移（服务器上用这个）
npm run migrate:status      # 看迁移状态
npm run prisma:generate     # 重新生成 Prisma Client
npm run db:seed             # 写入种子数据
npm run db:studio           # 打开可视化数据管理界面
```

**重置本机数据库**（会清空数据，开发期用）：

```powershell
npx prisma migrate reset --force --skip-seed   # --skip-seed 是必要的，见下
npx tsx prisma/seed.ts
```

> 说明：`package.json#prisma.seed` 这个配置项在 Prisma 7 会被移除，所以没有使用它，而是把 seed 直接写成 `npm run db:seed`（内部调 `tsx prisma/seed.ts`）。副作用是 `migrate dev` / `migrate reset` **不会自动跑 seed**，需要手动执行一次，因此重置时加 `--skip-seed` 保持行为一致。

## 9. 本机开发注意事项

1. **Prisma 命令需要启动它自带的引擎子进程**。在受限沙箱会话里这些命令会报 `spawn EPERM`，需要在正常终端（或放宽权限的会话）中执行。你自己的终端不受影响。
2. **npm 在沙箱会话里需要把缓存指到工作区内**：`npm install --cache .\.local\npm-cache`。同样，你自己的终端不需要这个参数。
3. 数据库连接串在 `apps/api/.env`（已被 `.gitignore` 忽略）；模板见 `apps/api/.env.example`。
4. 本机 PostgreSQL 的完整信息（服务名、启停、备份命令、中文 Windows 的 psql 编码坑）见 [02-本机数据库环境](02-本机数据库环境.md)。
